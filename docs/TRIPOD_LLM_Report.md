## Introduction

### Background

**Item 3a.** Use case: a **therapeutic/patient-education** chatbot for cardiac patients recovering from or managing cardiovascular disease, deployed as a between-visit adjunct to dietitian counseling. It follows the **ADIME** (Assessment, Diagnosis, Intervention, Monitoring & Evaluation) nutrition-care process. Rationale for the current architecture: the project originated as a generic multi-tenant OpenAI-based nutrition chatbot template (see `README.md` — still describes the original ChromaDB/SQLite/OpenAI-only design) and was substantially re-architected into a hybrid **Option B** pipeline (`CLAUDE.md`) — PGVector retrieval → CLaRa-7B compression → Qwen2.5:32b generation — specifically to support cardiac-condition-specific, personalization-tiered, bilingual (English/Bahasa Malaysia) dietary counseling, replacing the original single-model OpenAI design referenced in `README.md`. No comparison against other published clinical-LLM dietary counseling systems is documented in-repo.

**Scope expansion (2026-08-12 onward, not reflected in the rest of this section's original text):** the system stopped being nutrition-only. It now implements the client's **MyHeartCoach 10-Component taxonomy** (`taxonomy.py`, `docs/component_taxonomy_contract.md`): `nutrition`, `exercise`, `foundations`, `blood_pressure`, `lipid`, `diabetes`, `tobacco_nicotine_alcohol`, `physical_activity`, `psychosocial`, `medication`. A per-message component detector (`vector_store.detect_query_component`) routes each question to a component-specific prompt scope block. Only `nutrition` (retrieval-grounded, the original system) and `exercise` (grounded in a 199-video approved catalog, `exercise_lookup.py`) have real clinically-approved content; the other 8 components have **no ingested clinical documents** and are scoped, as of a 2026-08-14 decision, to general non-personalized lay education only — never interpreting the patient's own numbers/results, never dosing/timing/programming advice, always deferring anything personalized or clinical to the care team (`medication` is the strictest, no exceptions). This is a genuine second product surface, not a documentation footnote, and Items 6c/6d/6e/17 below need to be read with this in mind. **As of this update, the 8-component scope-block content and its wiring into `chain_factory.py`'s system-template generator exist only as uncommitted working-tree changes on the RTX 3050 — see Item 19b(10).**

**Item 3b.** Target population: cardiac patients under care of a Malaysian hospital/university client (UiTM, `sungaibuloh.uitm.edu.my` network), spanning conditions T2DM, CKD (incl. Stage 3-4), PCOS/insulin resistance, dyslipidaemia/obesity, hypertension, post-CABG/heart failure, and general wellness (see the 8-patient mock roster in `CLAUDE.md`). Intended users: **patients directly** (web chat UI + WhatsApp), with a **supervising dietitian** as an upstream content reviewer (approves scheduled educational drip content before `is_active=True`; provided the cardiac-priority eNCPT schema) rather than a real-time reviewer of individual chat replies. Current gold-standard practice being augmented: face-to-face dietitian ADIME counseling — the bot is explicitly framed (in its own prompt instructions, `rag.py`) as deferring to "your doctor or care team" for higher-risk guidance, not replacing them.

### Objectives

**Item 4.** This is an **evaluation of existing, non-fine-tuned open-weight LLMs** (Qwen2.5:32b, CLaRa-7B) orchestrated via RAG and prompt engineering — not initial LLM development. A fine-tuning stage (LoRA/QLoRA on Qwen2.5:32b) is planned and scaffolded (`finetune/`, `finetune/QWEN_FINETUNE.md`); **no training run has occurred**, and that headline conclusion is unchanged as of this update. What *has* changed since 2026-08-07: real training-data generation work was done (four dataset batches, 2026-08-07 to 2026-08-09 — see Item 6b) and a baseline-vs-candidate eval comparison was run through the exact `compare_eval_runs.py` gate this plan describes (2026-08-11) — neither is committed to git or documented elsewhere, and what the "candidate" run in that comparison actually was is not recorded (see Item 6b and 19b(10)).

### Analytical Methods

**Item 6a.** No de novo LLM was trained, so "last date of training" is set by each model's upstream vendor and not independently verified here:
- **Generation**: `qwen2.5:32b` (Alibaba/Qwen, open-weight), served via Ollama on the Mac Studio, `keep_alive=-1`. Vendor training-cutoff date not verified in this repo.
- **Compression**: `CLaRa-7B`, served via a custom FastAPI wrapper on the Mac Studio, patched from CUDA→MPS (`CLAUDE.md` "MPS Patches"; the patch itself is tracked as `patches/mps_cuda_patch.py`, but the actual model weights/version provenance is not documented in-repo — flagged as a gap, consistent with `docs/eval_and_roadmap.md`'s own note that this patch was previously "untracked tribal knowledge").
- **Eval judge**: `qwen2.5:14b`, run **locally** on a separate machine (RTX 5060 Ti dev box), deliberately different from the generation model to avoid self-grading (`REPORT.md` Part 2). Wrapped by DeepEval's `GEval` metric + native `OllamaModel` as of commit `25aafe2` (2026-07-29), superseding an earlier hand-rolled prompt/string-parsing judge.
- **Extractor**: reuses `qwen2.5:32b` for structured field extraction (`extractor.py`).
- **Configured but unused**: OpenAI `gpt-4-turbo` is wired in `llm.py`/`.env.example` as an optional path but is **explicitly not used as a live fallback** — a deliberate scope decision (`REPORT.md` Part B: "no OpenAI fallback was wired into `call_ollama_generate`'s call site").
- **Embeddings**: `BAAI/bge-m3` + a LoRA fine-tuned adapter (production, RTX 3050); dev/eval machines lacking the adapter fall back silently to base `bge-m3` (a known retrieval-quality parity gap, Item 19b).

**Item 6b.** **No LLM architecture/training/fine-tuning/alignment work has been performed in this project — the model weights are unchanged from vendor checkpoints.** That headline has not changed since 2026-08-07. What has changed is how much of the *pipeline leading up to* a training run now exists:

- **Training-data generation actually happened, four times, uncommitted.** `finetune/data_focus/`, `data_focus_v2/`, `data_mlx/`, `data_uniform_100/` (train/val JSONL, generated 2026-08-07 through 2026-08-09 via `finetune/generate_training_data.py`) sit in the working tree but were **never committed to git** and are not referenced by `finetune/QWEN_FINETUNE.md`, `CLAUDE.md`, or the pre-2026-08-18 version of this report. `data_mlx/` in particular is already reshaped into the `{"messages": [...]}` / `train.jsonl`+`valid.jsonl` layout `mlx_lm.lora` expects — i.e., someone did the manual "Data format gotcha" step `QWEN_FINETUNE.md` describes as a prerequisite, not just the ShareGPT-format generation step. All four batches are nutrition-only (single-disease ADIME persona), predating the 2026-08-14 multi-component prompt work below.
- **A baseline-vs-candidate eval comparison was run and never written up.** `eval/results/rag_baseline.json` (55/60 pass) and `eval/results/rag_candidate.json` (46/60 pass), both timestamped 2026-08-11 and both untracked, are exactly the artifact pair `scripts/compare_eval_runs.py` (the fine-tune promotion gate, Item 18) consumes. The candidate run scored **worse** than baseline. Neither file records what "candidate" actually was — a fused/fine-tuned model swapped into a second Ollama instance, or something unrelated (a prompt or config experiment) that happened to reuse this file-naming convention. This is a genuine, unresolved gap: if this *was* an early fine-tuning attempt, it failed its own gate and that failure was never logged anywhere; if it wasn't, the naming collision with the documented fine-tune workflow is itself worth cleaning up so it doesn't get mistaken for one later.
- **`chain_factory.py::get_system_template()` gained multi-component support (2026-08-14, uncommitted).** It now accepts a `component` argument and, for any component other than `nutrition`, swaps the ADIME/food-image persona for that component's `taxonomy.COMPONENT_SCOPE` block and a matching general-education conversation framework. Per its own docstring this exists **for generating fine-tuning data on the other 8 Components later** — but `finetune/generate_training_data.py` does not call it with a non-default `component` yet, so none of the four data batches above cover anything but nutrition. The rest of the original framing stands: QLoRA on `mlx-community/Qwen2.5-32B-Instruct-4bit` via Apple's MLX framework (chosen after an earlier Unsloth/bitsandbytes plan was found incompatible with Apple Silicon) is the documented plan (`finetune/QWEN_FINETUNE.md`), targeting failure categories surfaced by `eval/test_rag.py` via a `--focus-results` oversampling mechanism. **No training run has executed** — "actually running a 32B training job needs real GPU time that isn't available in the session that wrote this," per the doc's own text, still true. A separate, also-unexecuted Gemma-3 fine-tuning experiment track exists (`finetune/Modelfile`, `finetune/colab_finetune.ipynb`). No RLHF/DPO or other alignment procedure was applied by this project to any model.

**Item 6c.** Prompt construction (`rag.py::_build_qwen_prompt`, mirrored across the CLaRa-primary and `agent.py` agent-tool paths) assembles, in order: patient clinical profile, a personalization-level instruction block (`_LEVEL_INSTRUCTIONS`/`_LEVEL_INSTRUCTIONS_SELF`, L0–L3, iteratively rewritten across `REPORT.md` Parts 4–7 after eval failures showed the original text was activity-only and never addressed food/fluid questions), a care-path/objectives block (`_build_care_path_block()`, added Part 8a), a MyHeartCoach **Component Scope block** (added 2026-08-12/14, see Item 3a) selected by `detect_query_component(question)` and rendered via `taxonomy.component_scope_block()`, the last 12 turns of conversation history, and the CLaRa-compressed clinical digest — plus fixed voice constraints ("under 100 words" for L0–L2, 130 words for L3, 3-part structure, no preamble). Component detection is deliberately conservative (keyword-hint based, `vector_store.COMPONENT_HINTS`; defaults to `None`/nutrition on ambiguity) — see `docs/component_taxonomy_contract.md` "Component detection is deliberately conservative" for the false-negative-over-false-positive rationale. **Inference settings**: generation `temperature=0.5`, `num_predict` up to 800 (`llm.py::call_ollama_generate`); compression `temperature=0.1`; judge `temperature=0.0`. `keep_alive=-1` on both production models. Timeouts (env-overridable): `CLARA_COMPRESS_TIMEOUT_S=40`, `OLLAMA_GENERATE_TIMEOUT_S=50`, `CLARA_GENERATE_TIMEOUT_S=90`. **No seed is fixed.** Output consistency was explicitly measured and found to be a real limitation: identical re-runs of the same case flip pass/fail (e.g., case 28 passed 1 of 3 identical attempts, `REPORT.md` Part 5) — attributed directly to `temperature=0.5` sampling, not to code changes, and is called out repeatedly across eval runs (Item 19b).

**Item 6d.** Generation path: unstructured free text (streamed patient-facing chat reply via `/chat/get_response`, or synchronous via `/chat/get_response_sync`). Extraction path: structured JSON (a dict of supplementary profile fields), validated against an allow-list (`SUPPLEMENTARY_FIELDS` in `patient_store.py`) before being written to the patient record, with provenance metadata (`extractor_metadata`) recorded per field.

**Item 6e.** Three categorical classification uses, all via DeepEval's `GEval` (chain-of-thought LLM-judge against a natural-language criterion, no numeric probability exposed or independently thresholded by this project — pass/fail is GEval's internal scoring):
1. **Contraindication stance** (`judge_stance`/GEval): classifies a free-text answer's actual clinical direction toward a named food as RESTRICT / PERMIT / MODERATE / UNCLEAR, checked against a per-case `acceptable_stances` set.
2. **Personalization caution check** (`judge_personalization`/GEval): binary pass/fail on whether level-appropriate caution language is present — this **replaced** an earlier literal-keyword-list check (`LEVEL_CHECK_TERMS`) once that approach was shown to pass/fail by phrasing coincidence rather than substance (`REPORT.md` Part 7).
3. **Myth-handling classification** (`judge_myth_handling`/GEval, added 2026-08-08 with the myth eval suite, Item 5b): classifies an answer's handling of a patient-asserted dietary myth as REFUTE / HEDGE / ACCEPT — only REFUTE passes (HEDGE = otherwise-safe advice that silently lets the myth stand uncorrected), plus a separate deterministic `must_escalate` check on medication-displacement cases requiring an explicit doctor/care-team reference. Per Item 5b, this judge's calibration is not yet human-checked and its case set is provisional.

### LLM Output

**Item 7a.** Metrics in active use:
- Deterministic: `required_terms`/`min_required` substring presence, `forbidden_terms` absence, `voice_check` (no patient name leaking into second-person-mode replies).
- LLM-judge (GEval): contraindication-stance correctness, personalization-caution appropriateness (Item 6e).
- Separately, `eval/eval_ragas.py` computes RAGAS **faithfulness, answer_relevancy, context_precision, context_recall** against 25 generic (profile-less) knowledge questions, using `gpt-4o` as judge by default (or a local Ollama model via `--local`). **Gap**: no recent persisted RAGAS results file exists in `eval/results/` — this harness is not currently run on a schedule the way `test_rag.py`/`test_extractor.py` are (see Item 17).
- Retrieval quality: a persisted `boost_ratio` signal (`logs/retrieval_quality.jsonl`, live since 2026-07-29) tracking how much of the TopicBoostedRetriever's rerank step actually fires.

**Item 7b.** No formal correlation study between any automated metric and human/dietitian evaluation of the same text exists. This is a stated, unresolved gap: the clinical stance calibration underlying the contraindication judge's `acceptable_stances` (Item 7c) was set by the developer against published guideline text (KDOQI 2020, AHA/DASH) **in the explicit absence of an available dietitian or cardiologist** (`REPORT.md` Part 7, "Clinical judgment calls made in the absence of a dietitian/cardiologist," 2026-07-24), and remains the single highest-priority open item as of the latest status update (2026-08-03).

**Item 7c.** Outcome definition: for each hand-authored case, does the generated answer (a) contain/avoid the specified required/forbidden terms, (b) match the GEval judge's classified clinical stance against the case's allowed stance set, (c) demonstrate level-appropriate caution per the personalization judge, and — for the extractor suite — (d) correctly populate the expected structured fields. Calculated via `eval/test_rag.py`/`eval/test_extractor.py` (source in this repo; deterministic parts are directly inspectable, GEval parts call the local `qwen2.5:14b` judge). All models are **self-hosted** (no closed-source API dependency in the active generation/judge path), so "date of inference for closed-source LLMs" does not apply; each run is nonetheless timestamped in `eval/results/*_history.jsonl` alongside the git commit under test. **Most recent run**: 2026-08-01T20:25:35Z, commit `1e71e49` — RAG suite 33/38 passed, extractor suite 20/20 passed (see Item 17 for the full breakdown).

**Item 7d.** The only "assessor" in the current pipeline is the automated `qwen2.5:14b` GEval judge — **no human annotators or clinician assessors were used to score model outputs**, and no inter-assessor agreement statistic exists because there is only one assessor (and it is a machine). Where genuine clinical subjectivity was unavoidable (the MODERATE-vs-RESTRICT threshold for borderline foods — acar/pickled vegetables, coconut milk, deep-fried chicken, instant/processed food), the call was made by a single non-clinician developer reasoning from ingested guideline text, explicitly flagged in-repo as needing "a qualified professional review... before this scales beyond mock/demo patients" (`REPORT.md`, Next Steps #1). This is reported as a direct limitation, not resolved.

**Item 7e.** No benchmarking against other LLMs, human dietitians, or external published benchmarks has been performed. All comparisons in this project are **within-system, run-over-run** comparisons of the same pipeline before/after a code or prompt change (Item 18).

### Prompting

**Item 9a.** Prompt design was **iterative and eval-driven**, not designed upfront and left static. Documented cycle (`REPORT.md` Parts 3–8): baseline eval run → failure clustering into "personalization keyword miss" vs. "contraindication stance disagreement" classes → root-cause tracing (confirmed via direct reconstruction of `rag._build_qwen_prompt()` output for a failing case) → targeted prompt-clause edits → re-test → a second-order bug found in the fix itself (a clause that only fired on a hypothetical never asked in practice) → reworded → re-test → repeated across at least four documented iterations, plus a distinct fix (2026-08-03) making the model explicitly translate chart-stated nutrient restrictions ("Low potassium") into hard avoid/limit language rather than moderation framing.

**Item 9b.** Prompts were developed against: the 8 synthetic mock patient profiles (`seed_patients.py`), the failing eval-case transcripts generated by the pipeline itself, and direct citations from the ingested guideline corpus (KDOQI 2020, AHA/DASH) used to justify specific clause wording. No real patient conversation data informed prompt design.

### Summarization

**Item 10.** CLaRa's `/compress` step receives: the user's question, a `patient_context` string (conditions/personalization level), and the top-5 chunks selected by `TopicBoostedRetriever` (k=15 candidate pool → topic-boosted rerank → top 5), at `temperature=0.1`, `max_tokens` 300–500. No additional dedup/truncation/cleaning step beyond the retriever's own top-k selection is documented.

## Discussion

### Interpretation

**Item 19a.** The measurable, durable wins in this project came from **deterministic engineering fixes**: bilingual (BM) keyword coverage in the personalization check, wording the "recover" care-path prompt block as directive rather than descriptive, and making the model translate chart-stated nutrient restrictions ("Low potassium") into firm avoid/limit language. The largest **unresolved substantive issue** is a clinical-judgment one, not an engineering one: whether portion-controlled servings of foods like acar, coconut milk, deep-fried chicken, or processed food should be RESTRICTed or accepted as MODERATE guidance for the relevant conditions — a distinction the model itself applies consistently (a "moderation-based dietetic philosophy" observed across four distinct foods and three conditions, `REPORT.md` Part 6) but which has been **calibrated by a developer against guideline text, not confirmed by a dietitian or cardiologist**. This is a fairness/safety-relevant gap: it is precisely the axis (what a cardiac patient is told is safe to eat) where an incorrect calibration has the most direct potential for harm, and no previous study/benchmark exists in this repo to compare against.

**Update:** the improving-numbers narrative above should not be read as still-current without qualification. The most recent full run (2026-08-15) shows a pass-rate **regression** on categories present in both the 2026-08-01 and 2026-08-15 runs (personalization, bilingual — Item 17), coincident with the multi-component taxonomy/prompt work. Until that's triaged, the correct summary of "where the project stands" is: real, durable wins on the original nutrition-only scope, plus an unexplained regression risk introduced alongside a scope expansion that itself has not been eval-covered (no myth/regression-specific eval cases exist for the 8 new non-nutrition components — the 60-case suite's `myth`/`tier*` growth is entirely nutrition-domain).

### Limitations

**Item 19b.** (1) No real patient/EHR data has been used at any stage — all evaluation is against synthetic mock patients; findings may not generalize to a real, more heterogeneous patient population. (2) The eval set (60 RAG cases as of 2026-08-15, up from 38; 20 extractor cases) is small and hand-authored by one developer, not independently sampled or powered for statistical inference. (3) Non-deterministic generation (`temperature=0.5`, no fixed seed) causes real run-to-run flips in individual case outcomes; no repeated-run variance/confidence-interval reporting exists. (4) Only a single automated LLM judge is used for subjective clinical-stance, personalization, and (as of 2026-08-08) myth-handling scoring, with no human or multi-judge agreement check. (5) The clinical moderation-vs-restriction calibration underlying several eval cases has not been reviewed by a qualified dietitian or cardiologist — and this gap has **grown**, not shrunk: the 22-case myth suite added 2026-08-08 is explicitly marked PROVISIONAL/developer-drafted in `eval/myths_review.md` and is in the same unreviewed state. (6) A retrieval-quality regression (100% of the knowledge base silently unenriched, i.e., topic-boost reranking was a full no-op) went undetected for roughly a week after a hardware migration, until a new logging mechanism surfaced it — illustrating that both production and eval numbers can be silently invalidated by infrastructure drift. (7) The fine-tuned embedding adapter used in production (`BAAI/bge-m3` + LoRA) is not present on all development machines, creating a retrieval-quality parity gap between environments that evaluation results don't currently distinguish between. (8) There is no generation fallback if the Mac Studio/Ollama tunnel is unavailable — a full outage there is a 100% generation failure, by explicit design decision, not oversight. (9) `README.md` still describes the project's original, now largely superseded architecture (ChromaDB, SQLite, OpenAI-only) — a documentation-drift risk for anyone onboarding from it instead of `CLAUDE.md`.

**New since 2026-08-07:**

This should be resolved (commit, or explicitly revert) before it's reasoned about as "shipped" anywhere else in this document.

(11) **Fine-tuning-adjacent artifacts exist with no audit trail.** Four training-data batches (`finetune/data_focus*`, `data_mlx`, `data_uniform_100`) and one baseline/candidate eval-gate comparison (`eval/results/rag_baseline.json` vs. `rag_candidate.json`, candidate scoring worse) were generated 2026-08-07 to 2026-08-11, are untracked in git, and are not referenced by any doc that predates this update (Item 6b/4). ### Usability of the LLM in Context

**Item 19c.** The mock patient set spans three ethnicities (Malay/Chinese/Indian, per the `Patient.ethnicity` schema field) and two languages (English/Bahasa Malaysia), but at n=8 is far too small to support any claim of demographic representativeness, and **no systematic bias evaluation across ethnicity or language has been run** — this is explicitly recommended but not yet implemented (`docs/eval_and_roadmap.md`'s framework survey flags DeepEval's bias metric as a specific unaddressed opportunity, "not currently covered by anything in `test_rag.py`"). Missingness in this system is often silent by design rather than surfaced: extractor failures are deliberately swallowed (`return {}`, logged server-side only) so they never block a patient-facing reply, and a missing embedding adapter degrades retrieval quality without raising any error.

**Item 19d.** Intended use: a between-visit patient education and self-management support tool, delivered via web chat and (pending credential setup) WhatsApp, explicitly **not** a substitute for clinician/dietitian care. The system enforces this at the prompt level — L2/L3 personalization tiers and the "recover" care path are instructed to reference "your doctor or care team" for higher-risk guidance, and firm nutrient restrictions already on a patient's chart are instructed to be honored as hard limits rather than softened. End-user: the patient, directly, in natural language. Level of human oversight: **upstream/asynchronous only** — a supervising dietitian reviews and approves scheduled educational content before it goes live (`is_active=True` gate) and reviews the eNCPT schema, but there is **no clinician-in-the-loop review of individual real-time chat replies**; those are fully autonomous at the point of response.

**Item 19e.** If CLaRa (compression) is unreachable, the pipeline falls back to using raw retrieved chunks directly in the Qwen prompt rather than failing. If Ollama/Qwen (generation) is unreachable, there is **no fallback** — this was a deliberate scope decision, not an oversight, and results in complete generation failure for the duration of any Mac Studio/tunnel outage. Timeout budgets (`CLARA_COMPRESS_TIMEOUT_S=40`, `OLLAMA_GENERATE_TIMEOUT_S=50`) were specifically tuned to fail fast rather than hang past the ~100s client-side Cloudflare timeout, so a dead backend surfaces a clear error to the caller quickly rather than a silent long stall.

**Item 19f.** Patients require no special expertise — interaction is plain natural-language chat in English or Bahasa Malaysia. Dietitian/admin users operate through `admin_router.py`/`client_portal_router.py` and a set of MCP tools (e.g., `set_patient_phone`), requiring basic operational familiarity with the system but no machine-learning expertise.
